LEAD GENERATION SYSTEM — PROJECT STATUS / HANDOFF NOTES
=========================================================
Written for: continuing this build with a different (local) AI agent.
Everything below reflects the real state of the project, including bugs
that are fixed-but-unconfirmed and things that are flat-out broken.


1. THE GOAL
------------
Build a complete, ~$0 lead generation + CRM + outreach system, because
manual lead generation was too slow (hours for 8-10 leads).

Three components, working as one pipeline:
  1. Lead generation engine — finds leads matching an ICP automatically.
  2. CRM (Supabase) — stores every lead + every message + every reply,
     with enough detail that an AI can read one lead's full context and
     know what to say next.
  3. Message engine — drafts + iterates outreach (email/DM), with a
     feedback loop: what gets logged in the CRM should teach the system
     what messaging patterns actually get replies.

Hard constraints throughout: free tools only, prefer things that run
locally, no paid APIs unless there's truly no free alternative.


2. THE END GOAL
----------------
A mostly-automated pipeline: on a schedule, it finds new leads, scores
them against an ICP, writes qualified ones to the CRM, drafts outreach
messages using each lead's full context, and sends only the messages a
human has explicitly approved. The niche is SaaS founders/decision-makers
(not developers — this was a real correction made partway through: the
first working source, GitHub, was the wrong shape for the niche).


3. WHAT HAS BEEN BUILT (all files live in this leadgen/ folder)
------------------------------------------------------------------

ICP (Ideal Customer Profile) system:
  - icp_schema.py — Pydantic model + loader that validates an ICP JSON
    file. Nothing runs on an incomplete ICP.
  - example_icp.json — throwaway test ICP (Dhaka technical founders,
    used only to prove the pipeline mechanics work).
  - saas_icp.json — the REAL ICP: SaaS founders/decision-makers,
    8 countries, industry=SaaS. This is the one that should actually be
    used going forward.
  - icp-definition-schema.md — the human-readable field reference doc
    icp_schema.py is based on (given earlier in the chat, should be
    copied into this folder if it isn't already — the code doesn't read
    it directly, it's documentation).

Lead generation engine (5 stages, all wired in main.py):
  - models.py — RawCandidate: the shared shape every source adapter
    returns.
  - adapters/base.py — SourceAdapter interface every source implements.
  - adapters/github_adapter.py — Stage 2, working. Searches GitHub by
    location + job title keywords. Wrong niche fit (finds developers,
    not SaaS founders) but was useful for proving the pipeline works.
  - adapters/producthunt_adapter.py — Stage 2, BUILT BUT NEVER TESTED.
    Needs a free PRODUCTHUNT_TOKEN (from
    api.producthunt.com/v2/oauth/applications) that has not been
    obtained/tried yet. Much better fit for the SaaS niche — pulls
    makers of products under a topic (e.g. "saas").
  - enrichment.py — Stage 3. Guesses company domain (free Clearbit
    autocomplete), guesses + MX-checks an email, infers job title from
    bio text. Email verification hook exists but see section 5 (BROKEN).
  - scoring.py — Stage 4 (scoring). Weighted scoring against ICP fields
    (job title, geography, industry, pain indicators). Industry scorer
    uses a synonym list (not just literal word match) — this was a real
    bug fix partway through (it originally under-scored obvious SaaS
    companies that said "SaaS"/"B2B" instead of literally "software").
  - crm.py — Stage 4 (dedup) + Stage 5 (write). Dedup checks: exact
    email match, then exact source-URL match (this was added after a
    real bug — a lead called "Hackerman" with no email/company kept
    getting re-inserted every run because there was no dedup key for
    candidates missing both fields), then fuzzy name+domain match as a
    last resort. Writes qualified leads into Supabase `leads` table.
  - main.py — orchestrates all 5 stages. Run as:
        python main.py <icp_file.json> <limit>
    e.g. python main.py saas_icp.json 100

CRM (Supabase, 4 tables — schema given earlier in chat as crm-schema.sql,
should also be copied into this folder):
  - icp_profiles, leads, campaigns, interactions
  - migration_add_approved.sql — adds an `approved` boolean column to
    `interactions`. THIS IS THE HUMAN REVIEW GATE — nothing should send
    until a human flips a row's `approved` to true in Supabase directly
    (Table Editor). Confirm this migration was actually run.
  - seed_campaign.sql — creates one starter campaign row so there's a
    campaign_id to test the message engine with.

Message engine (message_engine/ folder):
  - gemini_client.py — calls Google Gemini, rotates across multiple API
    keys (comma-separated in .env) to spread load across your several
    Google accounts.
  - context_builder.py — pulls one lead's full record + entire
    interaction history from Supabase.
  - generator.py — builds the prompt (auto-detects first-touch vs
    follow-up based on whether history exists) and calls Gemini.
  - main.py — entry point. Two modes:
        python message_engine/main.py <lead_id> <campaign_id>
            interactive: shows draft, asks y/N/edit before logging
        python message_engine/main.py --batch <campaign_id> --status new --auto
            non-interactive (for automation): logs every draft with
            approved=false, for later human review in Supabase

Sending:
  - send_approved.py — only sends interactions where approved=true and
    sent_at is null. Sends via Gmail SMTP app passwords, rotating across
    multiple accounts (GMAIL_ACCOUNTS in .env, comma-separated
    email:app_password pairs). Tested once — ran successfully, found 0
    approved messages (expected, nothing had been approved yet).

Automation (n8n, self-hosted in Docker):
  - local_runner.py — a small Flask HTTP server that runs on the
    Windows host (NOT in Docker) and exposes /run-leadgen, /run-draft,
    /run-send. Exists because n8n's Execute Command node can't see the
    Windows filesystem/venv from inside its Docker container — n8n calls
    this instead over http://host.docker.internal:5005.
  - n8n-lead-gen-system.json — one importable n8n workflow with 3
    schedule-triggered branches on one canvas: generate leads (daily),
    draft messages (every 3h, auto mode), send approved (every 30min).
    IMPORTANT: has a placeholder "REPLACE_WITH_CAMPAIGN_ID" in the draft
    branch's request body that must be swapped for a real campaign id.
